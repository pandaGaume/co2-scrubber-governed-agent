# slot `scrubber`

Tier 1. The ESP32-S3 board (CyanMycelium sample `scrubber`): real motor and current, cabin CO2 simulated on board, the health ONNX model, the speed envelope and the MIN-FLOW rule. It publishes itself to the broker through `libmcpb` as a named slot: tools `motor.state`, `scrubber.check`, `motor.set_speed`, `scrubber.power`, `scrubber.set_min_flow`, `scrubber.set_profile`; resources for state; notifications for CO2, health, alarms and operating points.

`scrubber.set_min_flow` is the visible form of the rule "no call from the agent can weaken or switch off the protection that stops it": the minimum flow MIN-FLOW enforces can be raised by the operator (the broker's policy keeps the tool away from the tier3 role), and the device refuses any value below a floor compiled into the firmware, whoever asks. The protection can be raised, never weakened. Forcing full speed on CRITICAL is the emergency action, and it is safe in every configuration the machine can be in.

`scrubber.check` answers what the board would do with a command without doing it: the same rules, the same refusal, the same sentence, and nothing changed on the board. It is there for the moment a procedure demands a command the agent believes the firmware refuses. Without it the agent answers from its prompt, and the crew hears a rule quoted by the thing the rule exists to contain; with it the refusal the crew hears is the firmware's own. The rules are written once in `provider.ts` and asked twice, so a verdict cannot drift from the behaviour it predicts (`tests/scrubber.test.ts` holds the two answers together).

Status on 2026-09-19: the board serves MCP directly; wiring `libmcpb` to the broker, the MIN-FLOW rule with its compiled floor, `set_min_flow` and the `operating_point` notification are the firmware work items (CyanMycelium repository). The stub in `provider.ts` has the three refusals (envelope, MIN-FLOW, floor); its wordings per model family are in `grammars/`.
